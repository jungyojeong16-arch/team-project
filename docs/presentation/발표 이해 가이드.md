# ViewFit 중간 발표 이해 가이드

노션 발표 페이지에 적힌 내용을 **처음 듣는 사람도 설명할 수 있게** 풀어 쓴 것입니다.
노션과 같은 순서(1. 개발 환경 → 2. 프로그램 목록표 → 3. 구현 진도)로 되어 있고, 맨 끝에 스스로 확인하는 문제가 있습니다.

---

## 0. 먼저 큰 그림부터 (이것만 알아도 절반은 설명 가능)

### ViewFit은 한 문장으로
> 넷플릭스·티빙·웨이브 등 **여러 OTT에 흩어진 작품을 한곳에 모아**, **내 취향과 지금 상황에 맞는 작품을 추천**하고, 고르면 **그 OTT로 바로 보내 주는** 웹사이트

### 사이트는 "식당"처럼 돌아갑니다
| 식당 | ViewFit | 실제 이름 |
|---|---|---|
| 손님이 보는 홀·메뉴판 | 사용자가 보는 화면 | **프론트엔드** (Next.js) |
| 주방 (요리를 만듦) | 데이터를 계산·처리하는 서버 | **백엔드** (Django) |
| 창고 (재료 보관) | 회원·작품·평점이 저장된 곳 | **DB** (MariaDB) |
| 주문서 (홀 ↔ 주방) | 화면과 서버가 주고받는 약속된 요청 | **API** |
| 식재료 납품 업체 | 작품 정보를 주는 외부 서비스 | **TMDB API** |
| "이 요리는 옆 가게에서" 안내 | 작품을 볼 수 있는 OTT로 보내기 | **딥링크(바로가기)** |

### 사용자가 사이트를 쓰면 뒤에서 일어나는 일
1. 회원가입 → 화면이 서버에 "가입시켜 줘"(API) → 서버가 비밀번호를 **암호화**해서 DB `member` 표에 저장
2. 취향 설문 → 연령대·직업은 `member`, 좋아하는/싫어하는 장르는 `genre_preference`, 기억에 남는 작품은 `watch_history`에 저장
3. 홈 화면 → 서버가 내 취향 + 지금 시간대로 **추천 점수**를 계산해 오늘의 추천과 TOP 10을 보내 줌
4. 작품 클릭 → 상세 팝업 → [바로 보기] → 그 OTT의 검색 화면이 새 탭으로 열리고, `watch_history`에 "봤다"는 기록이 남음
5. 이 기록은 다음 추천에서 "이미 본 작품"으로 빠짐

## 1. 프로젝트 개발 환경

### 1.1 개발 환경 요약 — 표의 단어 풀이
| 단어 | 쉬운 뜻 | 질문받으면 |
|---|---|---|
| **Front-end** | 사용자 눈에 보이는 화면 부분 | "브라우저에 보이는 화면입니다" |
| **Next.js** | 화면을 만드는 도구(프레임워크). 주소마다 화면을 나눔 (`/ranking`, `/recommend` …) | "React로 화면을 만들고, 주소별로 페이지를 나눠 주는 도구입니다" |
| **React** | 화면을 **부품(컴포넌트)** 단위로 만드는 방식. 작품 카드 하나를 만들어 여러 화면에서 재사용 | "같은 작품 카드를 홈·랭킹·추천에서 똑같이 씁니다" |
| **TypeScript** | 자바스크립트에 "이 값은 숫자, 이 값은 글자" 같은 **타입 검사**를 붙인 언어. 실수를 미리 잡아 줌 | "화면 코드는 TypeScript로 써서 실수를 줄였습니다" |
| **Back-end** | 눈에 안 보이는 서버. 계산하고 DB에 저장·조회 | "화면이 요청하면 데이터를 처리해 돌려주는 부분입니다" |
| **Django** | 파이썬으로 서버를 만드는 도구. 로그인·관리자 페이지·DB 연결이 기본으로 있음 | "파이썬 웹 서버 프레임워크입니다" |
| **Django REST Framework (DRF)** | Django로 **API**를 쉽게 만들게 해 주는 도구. 로그인 **토큰**도 여기서 | "API와 로그인 토큰을 이걸로 만들었습니다" |
| **JSON** | 서버가 화면에 데이터를 보낼 때 쓰는 글자 형식 `{"title": "기생충", "year": 2019}` | "서버가 데이터를 이런 형식으로 보냅니다" |
| **API** | 화면과 서버 사이의 **약속된 주문서**. 주소 하나 = 기능 하나 | "`/api/v1/rankings/` 를 부르면 랭킹을 돌려줍니다" |
| **TMDB API** | 전 세계 영화·드라마 정보를 주는 외부 서비스 (The Movie Database) | "작품 제목·포스터·OTT 정보를 여기서 받습니다" |
| **포트 3000 / 8000** | 한 컴퓨터 안에서 프로그램을 구분하는 번호. 화면은 3000번, 서버는 8000번 | "같은 PC에서 화면과 서버를 따로 띄운 것입니다" |
| **AWS EC2** | 아마존이 빌려주는 **인터넷 컴퓨터**. 여기에 올리면 누구나 주소로 접속 가능 | "지금은 내 PC에서만 보이고, 배포하면 인터넷에서 보입니다" |
| **AWS RDS** | 아마존이 관리해 주는 **DB 컴퓨터** | "배포할 때 DB는 RDS에 둘 예정입니다" |
| **MariaDB** | 표(테이블) 형태로 데이터를 저장하는 DB 프로그램. MySQL과 거의 같음 | "관계형 DB입니다" |
| **utf8mb4** | 한글·이모지가 깨지지 않게 하는 글자 저장 방식 | "한글이 깨지지 않게 설정했습니다" |
| **Figma** | 화면 디자인 도구. 16개 화면을 먼저 그리고 코드를 거기에 맞춤 | "디자인을 먼저 정하고 그대로 구현했습니다" |
| **바이브 코딩** | 사람이 **무엇을 만들지** 정해서 AI에게 말로 요청하고, AI가 코드를 쓰면 사람이 **확인·수정 요청** | 아래 3.1 참고 |

### 1.4 외부 데이터
- **TMDB에서 받은 것**: 제목, 포스터, 줄거리, 장르, 관람 등급, TMDB 평점, **한국에서 이 작품을 볼 수 있는 OTT** 목록
- 받는 방법: 관리자가 `python manage.py import_tmdb` 명령을 한 번 실행 → 작품 200편이 DB에 들어감
- 6개 OTT(넷플릭스·티빙·쿠팡플레이·웨이브·디즈니+·왓챠) 어디에도 없는 작품은 **저장하지 않음** (볼 수 없으니까)
- **딥링크(바로가기)**: 원래는 "작품 페이지로 바로 이동"이 이상적이지만, **OTT들이 작품별 주소를 외부에 공개하지 않음** → 대신 "그 OTT에서 작품 제목으로 검색한 결과 화면"으로 보냄
  - 티빙·웨이브·왓챠: 검색 결과에 바로 나옴 ✅
  - 넷플릭스·쿠팡플레이: 로그인 화면이 먼저 나오지만 로그인하면 검색 결과로 이어짐 🟡
  - 디즈니+: 검색 주소 형식이 바뀌어 오류 ❌ → 고칠 예정

### 1.5 API 목록 (19개) — 묶어서 이해하기
**GET / POST / PUT 뜻**: GET = 가져오기(보기), POST = 새로 만들기·보내기, PUT = 통째로 저장(수정)

| 묶음 | API | 하는 일 |
|---|---|---|
| 기본 (0번) | `/health/` `/options/` `/contents/` `/home/feed/` | 서버가 살아 있나 확인 · 설문 선택지 목록 · 작품 목록 · 홈 화면 데이터 한 번에 |
| 회원 (1번) | `/auth/check-nickname/` `/auth/signup/` `/auth/login/` `/auth/logout/` | 닉네임 중복 확인 · 가입 · 로그인(토큰 받음) · 로그아웃(토큰 삭제) |
| 내 정보·설문 (3번) | `/me/` `/me/survey/` | 내 정보 보기 · 설문 저장 |
| 작품 탐색 (4번) | `/contents/search/` `/contents/<id>/` `/contents/<id>/watch/` | 제목 검색 · 작품 상세 · [바로 보기] 눌렀다는 기록 |
| 랭킹 (6번) | `/rankings/` `/rankings/generation/` | 통합 랭킹 · 세대별 랭킹 |
| 추천 (7번) | `/recommendations/` `/recommendations/refresh/` `/recommendations/pending-feedback/` `/recommendations/<id>/feedback/` | 맞춤 추천 TOP 50 · 추천 새로 만들기 · "어떠셨나요?" 물어볼 작품 · 그 답 저장 |

**토큰 로그인이란?** 로그인하면 서버가 **긴 비밀 문자열(토큰)** 을 줍니다. 화면은 그다음부터 요청할 때마다 이 토큰을 같이 보내서 "나 로그인한 OO야"를 증명합니다. (놀이공원 손목 팔찌와 비슷)

### ERD (DB 설계도) 읽는 법
**ERD** = DB에 어떤 표(테이블)가 있고, 표끼리 어떻게 연결되는지 그린 그림

| 표기 | 뜻 | 예 |
|---|---|---|
| **PK** (기본키) | 그 표에서 한 줄을 구별하는 **번호** (주민번호 같은 것) | `member.id` = 회원번호 |
| **FK** (외래키) | **다른 표의 번호**를 적어 두어 연결 | `rating.member_id` = 어느 회원의 평점인지 |
| **UK** (중복 불가) | 같은 값이 두 번 들어갈 수 없음 | 이메일, 닉네임 |
| **?** | 비어 있어도 됨 | 설문에서 "응답 안 함"이면 연령대가 빔 |
| 파란 머리 | 기본 정보 표 | 회원, 작품, 장르, OTT, 상황, 랭킹 |
| 초록 머리 | 두 표를 **잇는** 표 | 평점, 좋아요, 시청 기록, 추천, 장르 취향, 작품-장르 … |

**14개 테이블을 3묶음으로**
1. **기본 표 6개**: `member`(회원) · `content`(작품) · `genre`(장르 12개) · `ott_platform`(OTT 6개) · `tpo`(상황 5개) · `ranking`(랭킹)
2. **회원 ↔ 작품 표 4개**: `rating`(평점) · `content_like`(좋아요) · `watch_history`(시청 기록) · `recommendation`(추천)
3. **연결 표 4개**: `genre_preference`(회원 ↔ 장르) · `content_genre`(작품 ↔ 장르) · `content_platform`(작품 ↔ OTT) · `content_tpo`(작품 ↔ 상황)

**왜 연결 표가 필요한가? (N:M)**
한 작품은 장르가 여러 개(드라마 + 로맨스)이고, 한 장르에도 작품이 여러 개입니다. 이렇게 **양쪽이 여러 개**인 관계(N:M)는 표 하나에 담을 수 없어서, 가운데에 "작품번호–장르번호" 짝만 적는 표를 둡니다.

**설명하면 점수 받는 설계 포인트**
- **평가 당시 연령대 저장** (`rating.age_group_at_rating`): 작년에 20대였던 회원이 올해 30대가 되면, 회원 표의 연령대만 보면 그 사람의 예전 평점이 30대 평점으로 옮겨 감 → 그래서 **평점을 남기는 순간의 연령대를 평점에 따로 복사**
- **평균은 저장하지 않음**: 평균 평점·평가 수는 평점 표에서 그때그때 계산 → 원본이 바뀌어도 숫자가 틀어지지 않음
  - 예외: `ranking.score`(ViewFit 지수) — 그날 집계한 점수라 나중에 다시 계산하면 그날 값이 안 나와서 저장
- **비밀번호는 암호화(해시)** 해서 저장 → DB를 봐도 원래 비밀번호를 알 수 없음
- **별점은 0.5 단위만** DB가 받음 (4.3 같은 값은 DB가 거부)

## 2. 프로젝트 프로그램 목록표

### 2.1 프로그램 9개 — 사용자 입장에서
| 번호 | 프로그램 | 사용자가 하는 것 | 담당 | 진도 |
|---|---|---|---|---|
| 0 | 공통 기반 | (모든 화면의 상단 메뉴·하단·작품 카드, DB, 개발 환경) | 3명 | 85% |
| 1 | 회원관리 | 가입하고 로그인한다 | 정준교 | 100% |
| 2 | 작품 데이터 수집 | (관리자가 TMDB에서 작품을 모은다) | 홍준화 | 90% |
| 3 | 취향 설문 | 가입 후 5문항으로 취향을 알려 준다 | 홍준화 | 100% |
| 4 | 작품 탐색 | 검색하고, 상세를 보고, OTT로 이동한다 | 정재준 | 80% |
| 5 | 평가·좋아요 | 별점을 남기고 하트를 누른다 | 정준교 | 0% |
| 6 | 랭킹 | 통합 TOP 100, 세대별 TOP 30을 본다 | 정준교 | 98% |
| 7 | AI 추천 | 상황에 맞는 추천 50개와 이유를 본다 | 홍준화 | 100% |
| 8 | 마이페이지 | 내 활동을 보고 취향을 고친다 | 정재준 | 15% |

### 진도율 계산 방법 (질문 대비)
- 9개를 다시 **세부 프로그램 17개**로 나눔 (예: 6번 → 6-1 통합 랭킹, 6-2 세대별 랭킹)
- 세부 하나하나: 끝났으면 100%, 시작 전이면 0%, 진행 중이면 남은 일 비율로
- 17개를 평균 → **약 73%**
- 큰 프로그램 진도 = 그 안 세부 프로그램 평균 (예: 8번 = (8-1 30% + 8-2 0%) ÷ 2 = 15%)

## 3. 프로젝트 구현 진도

### 3.1 개발 진행 방식 — 단어 풀이
| 단계 | 쉬운 뜻 |
|---|---|
| ① 프로그램 목록 | 만들 기능을 번호 붙여 나눔 (회원가입은 1-1, 로그인은 1-2 …) |
| ② **PRD** | Product Requirements Document = **기능 설계서**. "왜, 무엇을, 어떻게 확인할지"를 적은 문서 |
| ③ 단계별 프롬프트 | PRD를 AI에게 보낼 **요청 문장**으로 나눈 것 (Step 1: API 만들기 → Step 2: 화면 만들기 …) |
| ④ 바이브 코딩 | 그 문장을 Claude Code(AI)에게 보내 코드를 받음 |
| ⑤ 완료 기준 확인 | PRD에 미리 적은 체크리스트를 **사람이 직접** 해 보고 통과하면 끝 |

**PRD 8개 항목**: 목적 · 사용자 이야기 · 기능 요구사항(FR) · 데이터·API · 규칙·예외 · **완료 기준** · 범위 밖 · 프롬프트

**작업 일지 (WORKLOG)를 만든 이유**
세 명이 각자 자기 AI를 쓰는데, **AI끼리는 서로의 대화를 볼 수 없습니다.** 그래서 정재준 팀원의 AI가 이미 있던 검색 기능을 한 번 더 만든 일이 있었습니다. → GitHub에 공용 작업 일지를 두고, **AI가 작업 전에 최근 일지를 먼저 읽고, 끝나면 일지에 기록**하게 했습니다. (`CLAUDE.md` = AI가 자동으로 읽는 팀 규칙 파일)

### 3.2 주차별 보고서 흐름 (말할 때 3단계로)
- 2~8주차: **기획** — 주제 변경(통학 비서 → OTT 큐레이션), 기능 목록, Figma, ERD, 기획 중간 발표
- 9주차: 개발 환경 선정, 역할 분담
- 10~11주차: **구현** — 회원·홈 → 랭킹·추천·설문·작품 데이터

### 3.3 PRD 예시로 설명할 기능들 (쉬운 예시 포함)

**① 통합 랭킹 (6-1) — ViewFit 지수**
> 지수 = **TMDB 인기도 70%** + **회원 평점 30%** (100점 만점)

- 인기도: 우리 작품 200편 중 TMDB에서 인기 1등이면 70점, 꼴찌면 0점 (순위 비율)
- 평점: 회원 평균 평점 5점 만점을 30점으로 환산
- **보정**: 평가가 2개뿐인데 둘 다 5점인 작품이 1위가 되면 이상함 → 평가가 적으면 **전체 평균 쪽으로 끌어당김**
  - 예: 평가 2개 평균 5.0, 전체 평균 3.5 → (2×5.0 + 5×3.5) ÷ (2+5) = **3.93점**으로 계산
- 주간 = 최근 7일 평점, 월간 = 최근 30일 평점
- 지난 집계와 비교해 **↑ 올라감 / ↓ 내려감 / NEW 새로 들어옴** 표시
- 영화 + 넷플릭스처럼 거르면 그 안에서 **1위부터 다시 번호**

**② 세대별 랭킹 (6-2)**
- 20대가 남긴 평점만 모아 작품별 평균 → 높은 순 TOP 30
- **평가가 3개 미만인 작품은 제외** (한두 명 의견으로 1위가 되지 않게)
- 기준은 "평가할 당시 연령대" (ERD 설명 참고)

**③ 맞춤 추천 (7-1) — 추천 점수**
| 조건 | 점수 |
|---|---|
| 내가 좋아하는 장르와 겹침 | 1개당 **+3** |
| 고른 상황(혼자 보는 밤 등)에 어울리는 작품 | **+4** |
| 기억에 남는 작품·좋아요·4점 이상 준 작품과 장르가 겹침 | 1개당 +1 (최대 +4) |
| 내 연령대 평균 평점 | **+평균 (0~5점)** |
| 싫어하는 장르, 이미 봤거나 평가한 작품, OTT에 없는 작품 | **아예 제외** |

- 예: 드라마 좋아하는 20대가 "혼자 보는 밤" 선택 → 드라마·스릴러 작품, 혼자 보는 밤에 어울림, 기억 작품과 장르 1개 겹침, 20대 평균 4.2점
  → 3 + 4 + 1 + 4.2 = **12.2점**. 이 점수 높은 순으로 50개
- **한 줄 이유**("혼자 보는 밤에 어울리는 스릴러 한 편"): 지금은 정해 둔 문장 틀에 상황과 장르를 넣어 만듦. 생성형 AI(LLM)는 비용·키 문제로 나중에 결정
- "AI 추천"이라고 부르지만 **지금은 규칙 기반 점수**라는 점을 솔직하게 말하는 게 좋음

**④ 재방문 피드백 (7-2)**
- 추천받은 작품을 [바로 보기]로 열고 **12시간 뒤** 다시 오면 "이번 작품은 어떠셨나요?" 팝업
- 별점을 주면 평점으로 저장, "아직 못 봤어요"를 누르면 다음에 다시 추천 후보

1. ViewFit을 한 문장으로 말하면?
   > 여러 OTT 작품을 한곳에서, 내 취향과 상황에 맞게 추천하고 그 OTT로 바로 보내 주는 웹사이트
2. 프론트엔드·백엔드·DB를 각각 무엇으로 만들었나?
   > Next.js(React, TypeScript) · Django(Python, DRF) · MariaDB
3. TMDB는 무엇이고 무엇을 받았나?
   > 영화·드라마 정보 외부 API. 제목·포스터·장르·한국 OTT 제공 정보, 작품 200편
4. 바로가기가 작품 페이지가 아니라 검색 화면으로 가는 이유는?
   > OTT들이 작품별 주소를 외부에 공개하지 않아서
5. PK와 FK의 차이는?
   > PK는 그 표 한 줄의 번호, FK는 다른 표의 번호를 적어 연결한 것
6. 평점에 '평가 당시 연령대'를 따로 저장한 이유는?
   > 회원 나이가 바뀌어도 예전 평점이 예전 세대에 남게 하려고
7. 연결 표(초록 표)가 필요한 이유는?
   > 작품–장르처럼 양쪽이 여러 개인 N:M 관계를 표 하나에 담을 수 없어서
8. 통합 랭킹 지수는 어떻게 계산하나?
   > TMDB 인기도 70% + 회원 평점 30%, 평가가 적으면 전체 평균 쪽으로 보정
9. 맞춤 추천에서 아예 빠지는 작품은?
   > 싫어하는 장르, 이미 봤거나 평가한 작품, OTT에서 볼 수 없는 작품
10. 전체 진도율과 남은 것은?
    > 약 73%. 남은 것은 5번 평가·좋아요, 8번 마이페이지, 그리고 AWS 배포
11. 바이브 코딩에서 사람이 한 일은?
    > 기능을 PRD로 정하고, 단계별로 요청하고, 완료 기준으로 직접 확인·수정 요청
12. 작업 일지(WORKLOG)를 만든 이유는?
    > 각자 쓰는 AI가 서로의 대화를 몰라 같은 기능을 두 번 만든 일이 있어서, 작업 전에 읽고 끝나면 기록하도록
