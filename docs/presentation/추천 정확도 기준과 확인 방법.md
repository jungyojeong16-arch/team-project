# AI 추천 정확도 — 기준과 확인 방법 (교수님 지적 4번)

- 11/24 중간 발표에서 교수님 질문: "AI가 추천하는 작품의 정확도 기준은 무엇이고, 어떻게 확인할 것인가"
- 7번 담당은 홍준화. 11/24 정준교가 제안하고, **11/25 홍준화가 정함**: 목표 숫자는 아래 제안값 그대로, ② 확인 명령을 만듦(`recommend_accuracy`), ③ 표시는 **구글 폼**(사이트 기능으로 넣지 않음). 남은 것은 ③ 참가자 모으기·폼 만들기 (4번)
- 관련 코드: `backend/core/recommend.py` (추천 점수), `backend/core/feedback.py` (7-2 재방문 피드백), `backend/core/management/commands/recommend_accuracy.py` (② 숨겨 두고 맞히기)

## 1. "정확하다"의 뜻
> **추천한 작품을 그 사용자가 실제로 좋아하는가.**
> "좋아한다"는 **별점 4.0 이상**으로 봅니다. 추천 점수에서 이미 4.0 이상을 '좋아한 작품'으로 쓰고 있어서(`LOVED_SCORE`) 같은 기준을 씁니다.

지금 추천은 기계 학습 모델이 아니라 **규칙 기반 점수**입니다 (7-1 PRD의 '처음 버전').
- 선호 장르 1개당 +3, 고른 상황과 연결되면 +4
- 기억에 남는 작품·좋아한 작품과 장르가 겹치면 1개당 +1 (최대 +4)
- 내 연령대 평균 평점 +0~5
- 비선호 장르와 이미 본 작품은 뺌

그래서 정확도는 **"이 점수 규칙이, 취향을 보지 않는 인기순보다 사용자가 좋아할 작품을 더 잘 골라 주는가"**로 판단합니다.

## 2. 확인 방법 4단계

| 단계 | 무엇을 | 어떻게 | 기준 (11/25 확정) | 언제 |
|---|---|---|---|---|
| ① 규칙 검사 | 설문 답을 제대로 지키는가 | 자동 테스트 | 비선호 장르 **0개**, 이미 평가·시청한 작품 **0개**, 상황을 고르면 **그 상황 작품만** | 지금 (테스트 있음, 통과) |
| ② 숨겨 두고 맞히기 | 계산이 의도대로 동작하는가 | 시연 회원이 4점 이상 준 작품을 하나씩 숨기고 추천을 다시 계산한 뒤, 숨긴 작품이 TOP 10 안에 들어오는지 (`python manage.py recommend_accuracy`) | **적중률이 인기순(통합 랭킹 순)보다 높을 것** | ✅ 11/25 홍준화 PC 통과 (13.4% > 8.6%) · 서버(MariaDB)에서도 한 번 |
| ③ 실제 사람 평가 | 진짜 사람이 좋아하는가 | 팀원·지인 10명 이상이 가입·설문 → 맞춤 추천 TOP 10과 통합 랭킹 TOP 10을 보고 **구글 폼**에 표시 | 추천 TOP 10 중 **6개 이상** "보고 싶다/봤고 좋았다", 그리고 **랭킹 TOP 10보다 높을 것** | 12/1~2 통합 테스트 |
| ④ 재방문 피드백 | 실제로 보고 나서 만족했는가 | 7-2 팝업에 남긴 별점을 DB에서 집계 | 별점 평균 **3.5 이상**, 4점 이상 비율 **60% 이상** | AWS 서버에서 사용 시작 후 ~ 12/8 |

### ① 규칙 검사 (지금 있는 것)
- `backend/core/tests.py`
  - `test_recommendations_follow_taste` — 선호 장르 작품이 위로, 비선호 장르는 빠짐
  - `test_rated_content_not_recommended_and_cross_age` — 이미 평가한 작품은 추천하지 않음
  - `test_not_watched_no_rating_and_recommended_again` — "아직 못 봤어요" 작품은 다시 추천
- 이것은 "맞게 만들었는가"를 보는 것이고, "사람이 좋아하는가"는 ③·④로 봅니다.

### ② 숨겨 두고 맞히기 (오프라인 평가)
```powershell
cd backend
python manage.py recommend_accuracy            # TOP 10 (약 1분 30초)
python manage.py recommend_accuracy --top 20   # TOP 20 안이면 적중
python manage.py recommend_accuracy -v 2       # 회원마다 적중 개수까지
```
1. 시연 회원 60명이 별점 4.0 이상 준 작품을 **하나씩 모두** 잠시 숨김 (평점·좋아요·시청 기록을 지움)
2. 그 회원의 추천 순서를 다시 계산 (7-1 과 같은 `recommend.rank_contents`, 저장하지 않음)
3. 숨긴 작품이 TOP 10에 있으면 적중 → **적중률 = 적중한 횟수 / 숨겨 본 횟수**
4. 같은 후보(이미 평가한 작품은 뺀 것) 안에서 **통합 랭킹 순 TOP 10**(취향을 안 봄)과 **무작위 10개**의 적중률도 계산해 비교
5. 지운 것은 바로 되돌림 → **DB는 바뀌지 않음** (테스트 `RecommendAccuracyTests` 로 확인)

**결과 (11/25 홍준화 PC, SQLite — 작품 200개 · 시연 회원 60명 · 숨겨 본 횟수 794번)**

| | 맞춤 추천 (7-1 점수) | 통합 랭킹 순 (비교) | 무작위 (기대값) |
|---|---|---|---|
| TOP 10 적중률 | **13.4%** (106번) | 8.6% (68번) | 5.9% |
| TOP 20 적중률 | **25.1%** (199번) | 14.6% (116번) | 11.8% |
| 숨긴 작품의 평균 순위 (후보 평균 169개) | **54위** | 78위 | 85위 |

→ 기준 "적중률이 통합 랭킹 순보다 높을 것" **통과**. 맞춤 추천이 통합 랭킹 순보다 약 1.5배, 무작위보다 약 2.3배 잘 맞힘.

- 처음 계획은 회원마다 1개만 숨기는 것(60번)이었는데, 해 보니 **어느 작품을 숨기느냐에 따라 적중률이 5~17%로 흔들리고** 통합 랭킹 순보다 낮게 나온 경우도 있었습니다. 60번은 너무 적어서, 4점 이상 평점을 모두 숨겨 보는 방식(794번)으로 바꿨습니다. 몇 번을 실행해도 같은 결과가 나옵니다.
- 적중률 숫자 자체가 낮아 보이는 것은, 후보가 약 169개인데 그중 딱 1개(숨긴 작품)를 TOP 10 안에 넣어야 맞는 어려운 시험이라서입니다. 그래서 숫자 하나보다 **통합 랭킹 순·무작위와 비교**해서 봅니다.
- **주의**: 시연 평점은 `seed_demo` 가 "연령대 취향 장르와 겹치면 점수를 높게" 만든 가상 데이터입니다. 그래서 ②는 **계산이 의도대로 도는지 확인하는 용도**이고, 정확도의 근거로 내세우지는 않습니다. 진짜 근거는 ③·④입니다.
- 통합 랭킹(`ranking` 표)은 미리 집계해 둔 것이라 숨긴 평점 1개가 지수에 조금 들어가 있습니다 (지수의 70%는 TMDB 인기도라 영향은 아주 작음).

### ③ 실제 사람 평가 (통합 테스트 때)
- 대상: 팀원 3명 + 지인 7명 이상 = **10명 이상** (서로 다른 연령대·취향이면 더 좋음)
- 순서: AWS 사이트에서 가입 → 설문 5문항 → **맞춤 추천 TOP 10**과 **통합 랭킹 TOP 10**을 보고 작품마다 하나 고르기
- 표시는 **구글 폼**으로 받습니다 (11/25 결정 — 사이트에 기능으로 넣으면 PRD 범위 밖이라 넣지 않음). 폼 구성(안):
  - 문항 1: 연령대 (설문과 같은 보기)
  - 문항 2: 맞춤 추천 1~10위 — 객관식 그리드 (행 1위~10위, 열은 아래 표의 4개)
  - 문항 3: 통합 랭킹 1~10위 — 같은 그리드
  - 응답은 구글 시트로 받아 ✅ 개수를 셈

| 표시 | 적중으로 셈 |
|---|---|
| 보고 싶다 | ✅ |
| 이미 봤고 좋았다 | ✅ |
| 별로다 | ❌ |
| 이미 봤고 별로였다 | ❌ |

- **적중률 = ✅ 개수 / 10**, 10명의 평균을 냄
- 결과 표 예시 (12/8 발표에 넣기)

| | 맞춤 추천 TOP 10 | 통합 랭킹 TOP 10 (비교) |
|---|---|---|
| 평균 적중률 | ○○% | ○○% |
| 6개 이상 맞은 사람 | ○ / 10명 | ○ / 10명 |

- 결과가 기준보다 낮으면 점수 비율(장르 +3, 상황 +4 등)을 조정하고 다시 확인합니다. 이것도 결과로 기록합니다.

### ④ 재방문 피드백 (서버에서 쓰기 시작한 뒤)
7-2 팝업에서 "봤어요"라고 답하고 남긴 별점은 평점(`rating`)으로 저장되고, 추천(`recommendation`)의 피드백 상태가 `rated` 가 됩니다. HeidiSQL에서 아래처럼 집계합니다.

```sql
-- 추천받고 본 작품의 별점 평균과 4점 이상 비율 (시연용 가상 회원 제외)
SELECT COUNT(*)                                    AS 응답수,
       ROUND(AVG(r.score), 2)                      AS 별점평균,
       ROUND(100 * AVG(r.score >= 4.0), 1)         AS 좋아함_비율
FROM rating r
JOIN member mb ON mb.id = r.member_id
WHERE mb.email NOT LIKE '%@demo.viewfit.local'
  AND EXISTS (SELECT 1 FROM recommendation rec
              WHERE rec.member_id = r.member_id
                AND rec.content_id = r.content_id
                AND rec.feedback = 'rated');
```

- 12/8까지는 응답 수가 적어서 **참고용**입니다. 몇 명이 몇 개를 답했는지 함께 적습니다.
- "아직 못 봤어요" 비율이 높으면 추천이 틀렸다기보다 **보러 가지 않은 것**이라 정확도 계산에서는 빼고 따로 적습니다.
